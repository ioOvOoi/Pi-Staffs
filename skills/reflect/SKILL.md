# Reflect

Reflect 是**只给 orchestrator** 用的复盘流程：回看近期会话、项目笔记与既有 agent 资产，然后只给出**最小有用**的改进建议——一个技能、一个自定义 agent、一条命令、一处配置改动、一条提示词规则、一份 playbook，或者「什么都不用加」。

目标是找出**真实重复**的摩擦，用证据说话，别为了显得勤快而造资产。

## 何时使用

用户要求：

- 复盘（`/reflect` 或 `/reflect <聚焦点>`）；
- 用 `--sessions` 做会话考古（`/reflect --sessions`、`/reflect --sessions --last 100`）；
- 从最近会话或重复流程里学点东西；
- 找出「我老是手工做」的事；
- 基于真实使用情况改进 pi-staffs 配置（配合 `pi-staffs` 技能）；
- 判断某个反复出现的流程是不是该固化成 playbook；
- 把重复的摩擦变成一个**更安全的默认值**。

**不要**用于：常规实现工作、一次性调试、宏观架构评审、或没有流程证据的「猜想要不要加个 agent」。

> 触发方式：本插件只注册 `/staffs`。用户说「复盘 / reflect / 看看我重复在做什么」时，就按本技能执行；`--sessions` 等参数按自然语言理解。

## 会话模式（`--sessions`）

把模式切到**会话考古**：跨所有项目分析 Pi 的历史会话，找出重复模式、摩擦与改进机会。

### 1. 找到会话

Pi 的会话按项目分目录存在：

```text
~/.pi/agent/sessions/<项目 slug>/<ISO 时间>_<会话 id>.jsonl
```

每个 `.jsonl` 是一行一个事件，第一行形如：

```json
{"type":"session","version":3,"id":"01a0…","timestamp":"2026-09-12T09:44:39.349Z","cwd":"C:\\Users\\<你的用户名>\\.pi"}
```

后续事件类型：`model_change`、`thinking_level_change`、`custom_message`、`message`（`role: user|assistant`，内容块 `text` / `thinking` / `tool`）。

列最近的会话（跨全部项目，按时间倒序）：

```bash
ls -t ~/.pi/agent/sessions/*/*.jsonl | head -50
```

要限定项目，就把 `*` 换成该项目目录。用户给了 `--last N` 就把 `head -50` 换成 `head -N`。

### 2. 读会话内容

用 node 解析 JSONL——**只读所需字段**，不要把整份会话读进上下文：

```bash
node -e '
const fs=require("fs");
const f=process.argv[1];
const lines=fs.readFileSync(f,"utf8").split(/\r?\n/).filter(Boolean);
const head=JSON.parse(lines[0]);
console.log("cwd:",head.cwd,"start:",head.timestamp);
for(const l of lines){
  let e;try{e=JSON.parse(l)}catch{continue}
  if(e.type==="model_change")console.log("model:",e.provider+"/"+e.modelId);
  if(e.type!=="message")continue;
  for(const b of (e.message?.content??[])){
    if(b.type==="tool")console.log("  tool:",b.toolName??b.name);
    if(b.type==="text")console.log("  "+e.message.role+":",String(b.text).replace(/\s+/g," ").slice(0,200));
  }
}
' "$HOME/.pi/agent/sessions/<slug>/<file>.jsonl"
```

要点：

- 只抽 `cwd` / 模型 / 用户消息 / 工具调用序列，用于判断目标、路径与摩擦；
- 大文件不要整体打印，**先看工具调用序列，再定点看几条消息**；
- 只看工作相关会话，个人目录/隐私内容跳过。

### 3. 每个会话产出一份结构化摘要

```json
{
  "session": "01a09501-34b4-72f3-8ef1-74142f40f3af",
  "project": "C:\\Users\\<你的用户名>\\.pi",
  "timestamp": "2026-09-12T09:44:39.349Z",
  "goal": "修 CI 失败",
  "success": true,
  "frictions": ["反复 grep 找测试文件", "跑了三次测试才通过"],
  "recommendations": ["加一条 /test-ci 命令"],
  "duration_minutes": 18,
  "models_used": ["ollama-cloud/deepseek-v4-flash:0731"],
  "agents_used": ["orchestrator", "fixer", "explorer"],
  "tools_used": ["read", "edit", "bash"],
  "confidence": 0.85
}
```

**置信度打分：**

- 0.9–1.0：成败明确、模式显眼；
- 0.7–0.9：结果大概率清楚，模式从工具使用推出来；
- 0.5–0.7：结果不确定、证据有限；
- <0.5：跳过，或标为「证据不足」。

### 4. 存储与缓存

摘要存到：

```text
~/.pi/agent/pi-staffs/reflections/sessions/<session-id>.json
```

**缓存逻辑：**

1. 先看该会话的 `<session-id>.json` 在不在；
2. 在 → 直接读（省 token）；
3. 不在 → 分析并写回；
4. 最后在所有摘要上聚合出报告。

### 5. 聚合

1. **按主题聚类**——摩擦相似的会话归到一起；
2. **计频**——「50 个会话里有 42 个在编辑前反复 grep」；
3. **按影响排序**——最常出现的建议优先；
4. **过滤噪声**——一次性的问题不进报告；
5. **交叉参考**——看模式是否跟特定模型、角色或仓库相关。

**范围分类：**

- **global**：所有仓库都适用（>50% 仓库出现）；
- **cross-repo**：只在特定几个仓库出现；
- **project-specific**：只跟一个仓库有关。

### 6. 输出格式

```text
会话复盘报告
分析最近 50 个会话，覆盖 8 个仓库。

分析的仓库：
- <repo>（<N> 个会话）
- …（另有 M 个）

发现
- <模式>：50 个会话中 N 个、覆盖 M 个仓库。
  - 范围：global | cross-repo(<repos>) | project-specific(<repo>)
  - 置信度：0.95
  - 影响：高 | 中 | 低

建议改动
- <资产>：<用途>
  - 范围：global | cross-repo(<repos>) | project-specific(<repo>)
  - 置信度：0.97
  - 预计省下的时间：高 | 中 | 低

跳过
- <候选>：现在不值得固化的原因。
  - 范围：<原因>
  - 置信度：<分数>

证据不足
- <候选>：还需要什么证据才能动手。
  - 当前范围：<已观察到的>
  - 需要的范围：<能确认的证据>
```

### 7. 出错怎么办

- 会话目录不存在 → 「`~/.pi/agent/sessions/` 下没有会话。先至少在一个项目里用过 Pi。」
- 会话文件为空 → 「<file> 是空的，没有可分析内容。」
- 某个会话读不出来 → 跳过并提示：「会话 <id> 读不出来，跳过。」
- 会话没有消息 → 跳过：「会话 <id> 没有消息。」

恢复原则：记下失败 → 继续处理剩下的会话 → 最后汇报「3 个会话因读取错误被跳过」。

## 核心契约

Reflect 必须**保守、以证据为准**：

- 先盘点既有资产，再提新东西；
- 优先看「近期、重复、用户能感知」的摩擦，别拿孤立事件说事；
- 只推荐**最小有用**的形态；
- 证据弱时，「什么都不加」就是成功结果；
- 改提示词、技能、命令、agent、MCP 权限或配置前**先征得同意**；
- 不要与既有资产重复；
- 说清生效方式：Pi 的配置/提示词/agent/技能/MCP 改动需要 `/reload` 或重启 Pi。

## 证据来源（按顺序）

1. 当前对话与用户的明确指令；
2. 项目内的指引与记忆：`AGENTS.md`、`.staffs/`（board / deepwork 进度 / 票面）、`codemap.md`、笔记；
3. 现有资产：`~/.pi/agent/skills/`、`~/.pi/agent/agents/*.md`、`~/.pi/agent/pi-staffs.json`、`~/.pi/agent/settings.json`、包内 `prompts/` 与 `skills/`；
4. Pi 会话文件或日志（可安全检视时）；
5. 仅当建议的流程依赖第三方工具/库、且行为需要确认时，才查外部文档。

尊重隐私与安全边界：不要翻无关的个人文件、凭据、私信或外部账号，除非用户明确要求且流程确实需要。

## 工作流

### 1. 盘点既有资产

提任何建议之前，先弄清已有什么：

- 包内技能与用户自装技能；
- 宿主 agent 定义（`~/.pi/agent/agents/*.md`）及其描述里的路由线索；
- 现有命令（`/staffs` 及其子命令）；
- `~/.pi/agent/pi-staffs.json`：当前档位、模型路由、技能与工具权限；
- 项目 playbook、文档、`codemap.md`、本地流程笔记。

已有资产能覆盖时，建议「扩展/使用它」，而不是造一个近似重复品。

### 2. 找重复模式

重复信号例如：

- 同一串命令在多份会话里反复出现；
- 用户反复要求同一类评审、初始化、发版或调试流程；
- 同一步手工调研/上下文收集反复发生；
- 同一个专才路由判断反复需要（该角色化）；
- 同一条项目规则反复被重新解释；
- 反复失败的原因始终是某 agent 缺少一条稳定指令、工具或权限边界。

强候选通常满足：至少出现**两次**、输入稳定、输出明确、有明确终止条件。

### 3. 给候选打分

对每个候选判断：

- **频率**：出现多频繁？
- **成本**：浪费了可观的时间、上下文、钱或注意力吗？
- **风险**：执行不一致会导致 bug、回归、错误决策或不安全改动吗？
- **稳定性**：输入与期望输出可预测吗？
- **覆盖**：已有资产是否已经处理得很好？

只有置信度高时才建议新建或修改资产。

### 4. 选最小有用形态

用**能解决问题的最弱形态**：

- **提示词/配置规则**：对既有 agent 的小行为改动；
- **技能**：针对某类任务形状的可复用流程指引；
- **命令**：输入稳定、可重复手动触发的动作；
- **自定义 agent**：有明确委派规则的独立专才车道；
- **MCP/工具权限调整**：给既有 agent 的安全访问调整；
- **项目 playbook/文档**：自动化过重时，给人看的流程指引；
- **跳过**：证据弱、一次性、含糊、敏感或已被覆盖的事。

能用提示词规则/技能解决，就不要建自定义 agent；能用短 playbook 解决，就不要写技能；收益不清楚，就不要动配置。

### 5. 先提议，后改动

除非用户已明确要求某个具体改动，先给一份简短提议：

```text
找到 2 个强重复流程，1 个弱候选。

建议：
- 给 orchestrator 加一条小规则处理 <流程>，因为 <证据>。
- 扩展既有技能 <skill>，不要新建，因为 <重叠>。

跳过：
- <候选>，因为它只出现过一次。

按这个改吗？
```

应用改动时：保留用户既有设置，优先**窄而追加**的编辑。

## 输出格式

```text
发现
- <流程>：证据、频率/置信度、建议形态。

建议改动
- <资产/配置/文档>：一句话用途，以及为什么这是最小有用形态。

跳过
- <候选>：现在不值得固化的原因。

证据不足
- <候选>：还需要什么才能动手。
```

什么都没有时，就说：

```text
没找到强重复流程。现在不建议新增或改动任何可复用资产。
```

## 护栏

- 不要为了凑流程而造资产；
- 不要造重叠的技能或 agent；
- 不要默默改全局配置、提示词或权限；
- 不要加让 agent 更激进、更贵、更爱插手、而收益不明的宽泛指令；
- 除非用户明确要求固化某条流程，不要只凭一个会话下结论；
- 生成资产时不要用隐私/敏感材料当例子；
- 改了配置、提示词、agent、技能、MCP 或插件文件后，告诉用户：「下次 Pi 运行生效；要立刻生效就 `/reload` 或重启 Pi。」
