# Deepwork

Deepwork 是**重活专用**的 orchestrator 流程。只在下面这类情况下启用：

- 有多个互相依赖的阶段；
- 跨模块的架构性改动；
- 不能部分交付的迁移（半成品上线会出事）；
- 需要多个专家车道持续协同。

**不要**因为「改了多个文件」就上 Deepwork。琐碎编辑、快速改文档、简单修 bug、边界清晰的常规功能，都不用。

## 核心契约

Deepwork 激活后，orchestrator 的角色是**调度者**，不是默认实现工。实现尽量派给 fixer / designer，orchestrator 负责切阶段、定验收、盯门。

## 状态文件

- 进度文件固定放在 `.staffs/deepwork/`；
- 代码与文档产物放到项目自己的路径（`src/`、`docs/`…），`.staffs/deepwork/` **只放进度文件**。

```text
.staffs/deepwork/<任务短名>.md
```

建这个文件之前——也就是规划和派发之前——先看一眼既有 `.gitignore` 与 `.ignore`：只补缺失行，别重复、别动无关规则。

`.gitignore`：

```gitignore
# BEGIN pi-staffs deepwork
.staffs/deepwork/
# END pi-staffs deepwork
```

`.ignore`：

```ignore
# BEGIN pi-staffs deepwork
!.staffs/
!.staffs/deepwork/
!.staffs/deepwork/**
# END pi-staffs deepwork
```

这两块让 deepwork 状态只留在本地，同时工具仍读得到它。

### 进度文件该写什么

**不要套死模板**——用最贴合当前工作的 markdown 结构。它只需要满足一个条件：作为会话状态长期可用。通常要包含：

- 当前目标与理解；
- from librarian 的已核实事实（写进来，省得 oracle 自己去查一遍）；
- 计划草稿、oracle 复审预算与门、复审记录；
- 实现阶段与状态；
- 验证结果；
- 未决问题、阻塞、待办。

在「重大决策、采纳调研、完成复审、阶段结束、验证结果、范围变更」之后更新它。已采纳的结论要记下来，本地文件用路径引用，**不要粘贴内容**。

## 规划

- 动手前先出计划；
- 计划要分阶段（实现 / 派发）；
- 派发前，按**依赖关系与自然交付边界**切出少量内聚阶段；不要为了「让 oracle 少看点」而切碎；
- 执行前定好交付阶段，并给每个阶段配一个**强制的 oracle 复审门**；把阶段顺序、专才归属、门顺序与一句话理由记进进度文件，并给用户一份精简版；
- 每个阶段开工前，用该阶段的可交付任务替换当前看板任务（`staffs_task`）——不要把上个阶段的残骸留在看板上。

## 阶段执行

- 每个实现阶段开工前，先定执行路径：哪些能并行、哪些必须串行、派给哪些专才、同一个专才是否要拆成多条有界车道。

### 调度纪律

全程用调度者模式：

- 记下任务/会话 ID 与归属边界（`staffs_task` 看板 + attempt 记录）；
- **等完成通知**，不要轮询运行中的后台任务；
- 后台任务在跑时不要卡住 orchestrator 车道；若确实没有独立工作可做，就短暂停下，让完成事件把流程唤醒；
- 相关任务还在跑、或终态结果还没核对时，**不要**推进到下一阶段。

## 阶段门与提交

- 每个阶段结束后：跑相关验证 → 更新进度文件 → 请求该阶段的 oracle 门；
- 请求 oracle 之前，先把已采纳的调研与文件引用写进进度文件/提示词，让 oracle **复审既有上下文**，而不是从零开始重新摸索；
- 给 oracle 的上下文包括：阶段目标、改动路径、验证证据、要它判的具体决策或风险；
- 若某阶段改了模块边界、依赖方向或文件归属，另派一个 explorer 结构扫描，与 oracle 门并行；
- 复审意见要合议：实质问题做**一轮有界**修复，再用针对性证据验证这一轮；
- 阶段若是独立可交付边界，就在进入下一阶段前打一个聚焦的提交。

### Oracle 复审次数

每个门：1 次初审 + 最多 2 次复-review。只在「修复实质上改变了被复审的决策/风险」或「原问题无法用聚焦证据验证」时才请复-review。机械改动、已验证过的改动，不要浪费复审次数。

每次请求 oracle 都写明第几次，例如：

```text
Gate 2 —— review attempt 2 of 3（还剩 1 次复-review）
```

复-review 时告诉 oracle：优先看未解决的实质问题、修复引入的新风险、以及旧问题是否已解决；**不得**重开已采纳、未改动或已解决的议题。两次复-review 用完后仍有实质风险，就记进进度文件并问用户：接受风险、改范围，还是特别授权再加一次复审。

## Designer 交付的护栏

当某个阶段包含 designer 时，它产出的 UI/UX 视为**后续阶段的设计意图**，重要设计决策要在继续之前写进进度文件。

designer 干完之后：

- 保持布局、节奏、层级、动效、间距、配色、可感知反馈、响应式与组件手感；
- 文案可以改得更自然贴切，但**不要**动视觉结构与交互意图；
- 后续的视觉、响应式、动效、层级、打磨、组件手感改动，一律回到 designer；
- fixer 只做「完全保持设计不变」的有界机械活：接线、测试、类型修复、非视觉行为改动；
- 若设计意图必须改，先记进进度文件再改。

## 收尾

- 以最终验证 + 一份精简总结结束。
