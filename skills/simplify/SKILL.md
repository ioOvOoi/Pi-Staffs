# 代码简化（Code Simplification）

## 概述

通过降低复杂度来简化代码，同时**严格保持行为不变**。目标不是更少的行数，而是更容易读、理解、修改和调试的代码。每次简化都要过一道测试：「一个新同事会比重读原版更快看懂它吗？」

## 何时使用

- 功能已经能跑、测试也过，但实现明显比需要的更沉重时
- 代码评审里被指出可读性或复杂度问题时
- 遇到深层嵌套、超长函数、含义不清的命名时
- 重构「赶时间写出来」的代码时
- 把散落在多个文件里的同类逻辑合起来时
- 合并后引入了重复或不一致时

**何时不要用：**

- 代码已经干净可读——不要为了简化而简化
- 你还不清楚这段代码在做什么——先理解再简化
- 代码是性能关键路径，而「更简单」的写法可测地更慢
- 你马上就要整体重写这个模块——简化一次性代码是白费力气

## 五条原则

### 1. 严格保持行为

只改表达方式，不改做什么。所有输入、输出、副作用、错误行为与边界情况都必须一模一样。只要你不确定某个简化是否保持行为，就别做。

每次改动前问：

- 它对每个输入都产生同样输出吗？
- 它保持同样的错误行为吗？
- 它保持同样的副作用与顺序吗？
- 什么样的**相称**的最终状态验证能揭示行为变化？

### 2. 遵循项目约定

简化的意思是让代码更贴近代码库的既有风格，而不是把你的外部偏好强加进去。

动手之前：

1. 读 `AGENTS.md` / 项目约定（本仓库：中文注释解释「为什么」，标识符英文）
2. 研究邻近代码如何处理同类模式
3. 对齐项目的导入、命名、函数风格、错误处理与类型标注习惯

破坏项目一致性的「简化」不是简化，是折腾。

### 3. 清晰优先于聪明

当紧凑写法需要读者停顿一下才能解析时，显式代码更好。

- 用可读的控制流替换嵌套三元表达式
- 用有名字的中间步骤替换密集的行内变换（当它能说明意图时）
- 该有的名字就留着，多几行无所谓

### 4. 保持平衡

警惕过度简化：

- 不要把承载含义的名字内联掉
- 不要把不相关的逻辑合并进一个大函数
- 不要删掉为可测试性或可扩展性服务的抽象
- 不要为了行数牺牲可理解性

### 5. 只动改动过的范围

默认只简化最近修改过的代码。除非明确要求，不要顺手做无关的重构。

## 流程

### 第 1 步：先理解再动手

在改动或删除任何东西之前，先理解它为什么存在。

回答：

- 这段代码的职责是什么？
- 谁调用它？它调用谁？
- 边界情况与错误路径有哪些？
- 有测试定义它的预期行为吗？
- 它当初为什么可能被写成这样？

答不上来，就先读更多上下文。

### 第 2 步：找简化机会

信号：

- 深层嵌套
- 职责混杂的长函数
- 嵌套三元表达式
- 布尔开关参数
- 重复的条件分支
- 含糊或误导性的命名
- 重复逻辑
- 死代码
- 不带来价值的包装与抽象

### 第 3 步：增量地改

一次只做一个简化。

每做一次：

1. 落地这次改动
2. 用相称的最终状态验证检查行为是否保持
3. 只有证据支持「行为保持」时才留下

尽量把重构与功能改动分开。

### 第 4 步：验证结果

简化之后确认：

- 代码确实更容易理解了
- diff 干净、可评审
- 仍然符合项目约定
- 行为、错误处理、副作用都没变

## 本仓库的具体指引

- 优先直白的 TypeScript，不要炫技式压缩
- 保留既有运行时行为、测试与钩子
- 当显式命名与更小的聚焦函数能提升可读性时，就用它们
- 重构严格限定在当前任务或评审意见的范围内

## 最终状态验证

用一份相称的最终状态验证计划检查最终 diff：跑仓库与发版要求的检查（本仓库 `npm run typecheck` + `npm run smoke`），只在改动范围或明确的不确定性需要时才增加或重跑证据。

## 与 omo-slim 原版的差异

- 「本仓库的具体指引」一节按本仓库改写（其余原则逐条保留）。
- 最终状态验证指向本仓库的命令，机制与原文一致。
